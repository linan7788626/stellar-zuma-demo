## 结论

项目适合继续采用**原生 Canvas 游戏 + HTML 教学界面**。当前最有价值的提升，是让赫罗图真正承担学习任务、建立一致的课程状态，并让游戏与知识面板使用清晰的布局空间。

### 关于之前的 Retina / HTTP 问题

隔离浏览器配置、相同 CSS 视口下，比较了 `file://` 与 HTTP，以及 DPR 1 和 2：**各面板 CSS 几何一致，逻辑坐标缩放正确**。测试服务也逐字节核对了 HTML、CSS、JS 与本地文件。

因此，不能将之前的问题归因于“缺少 Retina 缩放”或“HTTP 自动放大”。本次确认的是上述真实布局缺陷。旧浏览器配置中的站点缩放、缓存、端口上实际服务的项目仍可能造成差异，但没有证据认定其中某项就是当时的原因。没有修改用户的浏览器配置或停止其他项目服务。

## 3. 框架与代码结构建议

### 优先保留原生 Canvas

现有规模下，切换 React/Vue 或游戏引擎不会自动解决状态一致性、课程语义和布局问题。建议先让现有实现形成少量高内聚的 Module；桌面离线教学继续保留双击 `index.html` 的体验。

如果以后改用 ES Module / Vite，要明确接受本地服务或构建分发的工作流变化。当前可先用按顺序加载的普通脚本与一个命名空间隔离 Module，保持 `file://` 可用。

### 建议拆分顺序

| Module | 小而明确的 Interface | 隐藏的 Implementation |
| --- | --- | --- |
| Curriculum | `getLesson(id)`、`pickQuestion(lessonId)` | 关卡目标、阶段、例星、参考来源、题库、游戏映射 |
| Session | `startLesson(id)`、`dispatch(command)`、`step(dt)`、只读快照 | 状态迁移、暂停、胜负优先级、重试和下一课 |
| Engine | `step(dt, commands)` 返回状态与事件 | 轨道、碰撞、插入、合并、目标阶段、技能；不操作 DOM |
| HRDiagram | `draw(context, model, highlight)` 与同模型的命中检测 | 坐标变换、轴、区域、轨迹、选关；避免三套图彼此漂移 |
| View | `render(snapshot)` | Canvas、HUD、卡片和输入坐标换算 |
| Progress | `load()`、`recordLessonResult(result)`、`save()` | 默认槽位、迁移、存储失败处理、得分与学习记录 |

先统一课程数据和 Session，再抽取物理 Engine、赫罗图绘制。不要仅按行数把大文件拆成互相读写全局变量的小文件。游戏规则与 DOM 之间的 Seam 应传递“收集/阶段完成/作答”等事件，使同一条规则可以独立验证。

`__suma` 当前会暴露可写数组和修改配额的方法，适合开发调试。后续可收敛为稳定的命令与只读快照 Interface，再迁移回归测试；无需为单纯拆文件增加运行依赖。

## 4. 教学设计与赫罗图建议

### 最重要的教学闭环

每课围绕一个可观察的问题：**提出预测 → 操作游戏 → 赫罗图提供证据 → 用一句话解释 → 换个情境再判断**。

例如：“两颗星温度相同，谁更亮？”让学生比较主序星与巨星在同一横坐标上的位置，再通过 `L ∝ R²T⁴` 推出半径区别。相比不断记忆颜色，这更接近理解赫罗图。

### P1：把图表从进度装饰升级成学习工具

1. 统一使用 `log(T_eff)` 与 `log(L/L☉)` 映射，左热右冷。所有例星、区域、轨迹和等半径线共用坐标模型，并给出太阳 `T≈5772 K、L=1 L☉` 的锚点。
2. 数据独立记录 `spectralType`、`luminosityClass`、`evolutionStage`、`temperature`、`luminosity`、`radius`、`source`。球色/球尺寸只作为游戏映射，不能充当物理数据。
3. 明确区分“分类图中的不同恒星”与“同一颗恒星随时间移动”。O→M 的收集顺序和三种区域关卡都不是演化轨迹。
4. 当前手写轨迹只做定性示意。正式课程应增加核心氦燃烧、AGB、白矮星冷却以及大质量星终末分支，并标明质量、金属丰度和时间跨度；不要按动画播放时间暗示各阶段持续时间相等。
5. 题目绑定本课目标与常见误解。把“第一次是否答对、重试后是否理解”与游戏得分分开记录；增加间隔复习，而不是只记录点亮一次。

### P2：课堂与自学模式

- 课堂演示可自由选关、暂停讲图、比较两类星；自学模式保留循序解锁。
- 提供练习难度或关闭失败压力的学习模式，使知识阅读不与躲避黑洞争抢注意力。
- 给章节完成后的“我学会了什么”摘要，而不只显示积分奖励。

## 5. 主界面布局与后续交互建议

本次主界面已采用两栏布局：

```text
┌──────────────────────────────────────────────┐
│ 星链祖玛        得分 / 关卡        收集进度    │
├──────────────────┬───────────────────────────┤
│ 赫罗图与读图提示 │                           │
│                  │     正方形星链游戏区      │
│ 当前恒星知识     │                           │
│ （可独立滚动）   │  换球 · 暂停 · 按住加速   │
└──────────────────┴───────────────────────────┘
```

桌面舞台最大宽 1240px、高 860px，并随窗口尺寸收缩。学习栏宽 280–360px；画布同时受可用宽度和高度约束，保持正方形。≤860px 时变为单栏，游戏在前、学习内容在后。换球、暂停、加速提供独立按钮，触控高度至少 44px。介绍和问答卡限制可见高度并在内部滚动。

学习栏赫罗图的文字按实际显示宽度补偿缩放，保持约 12–13px，而不是随整张画布缩成约 6px；改变窗口大小时重新绘制。小图保留等半径辅助线，数值标注放在关卡大图中，避免与光谱型及区域名称挤在一起。

后续建议：

1. **图表可放大且阅读时暂停**：小尺寸迷你图适合定位，不适合精确读数。增加放大入口，展示完整轴与解释。
2. **视觉层级**：游戏中常驻当前学习问题和一条结论；例星、谱线、公式放入展开层。标题页可缩成“开始 / 继续 / 学习地图”，长说明分散到对应章节。
3. **可访问性**：已有字母/形状双重编码、图表文字说明和按钮可见焦点；后续增加完整键盘选关、减少 Canvas 动态效果设置和图表数据表。
4. **HiDPI 后续优化**：当前固定逻辑视窗方案有效。跨显示器或浏览器缩放时，可以根据显示尺寸与 DPR 更新 backing store，并同步设置视窗缩放和平移。主画布逻辑宽高现为 800×800，不能再以原世界宽 1280 计算显示比例。
